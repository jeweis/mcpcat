# 查看 MCP 诊断日志

使用管理员（WRITE）API Key 登录，打开左侧 **诊断日志**。
测试台连接失败、工具列表加载失败或没有返回工具时，也可以点击 **查看此服务日志**，
直接筛选当前 MCP 服务。

1. 保持或选择对应服务，重新操作以复现问题。
2. 刷新日志，按最低级别、时间范围或错误关键词缩小范围。
3. 展开记录查看异常类型、异常链和发生阶段；使用复制按钮复制脱敏日志。

可看到服务状态变化、初始化连接、工具发现、测试操作异常，以及应用和 MCP 库的警告/错误。
stdio 上游进程的标准错误输出也会被采集：例如 `npm error ENOTEMPTY`、包安装失败、
数据库连接错误等。stderr 本身不等于失败，明确以 npm error、ERROR、Fatal 或
Traceback 开头的输出会标记为错误，其余默认以警告级别显示。
未声明 tools 能力与返回空工具列表分别记录，便于区分不支持工具、确实没有工具和发现失败。

日志仅保留 **当前进程最近 1000 条**，重启后清空；刷新不会读取过去的容器日志。
多进程部署时每个进程独立保留。单条异常详情最多 16000 字符，超出会标记截断；
stderr 单行超过 4096 字符会省略内容，避免无限输出耗尽内存。

页面仅管理员可见，普通只读用户需要联系管理员协助。
已配置的凭证、上游环境变量/认证头和 URL 查询参数会脱敏；
不主动采集工具参数或返回正文。上游自行打印的任意业务内容仍可能出现在 stderr，
转发日志前应检查内容。建议上游避免输出数据库记录等业务数据。

## npx 首次启动超时或 ENOTEMPTY

若测试台显示初始化超时，同时 stderr 出现 npm `_npx/.../node_modules` 下的
`ENOTEMPTY`，优先检查 npm 安装缓存。多个上游操作可能启动独立 stdio 进程，
并发首次安装同一个包会放大缓存冲突风险。HTTP 200 仅表示传输请求成功，
不能证明上游已经初始化并返回工具。

应用现已将 npx 的启动与协议协商串行排队，启动等待预算为 120 秒，
协商完成后工具操作仍可并行；用户会话保持独立。启动失败会返回错误并记录详情。
这不会自动修复已经损坏的缓存。

如仍出现上述缓存错误，先停止相关服务和测试连接，保留 npm debug 日志，再由容器维护者处理对应损坏缓存、
在同一运行用户下串行预安装固定版本；安装完成后再重试。长期可在镜像构建时
安装固定版本，并直接运行已安装的可执行文件，避免请求时临时下载。
不要在安装仍进行时删除缓存或反复点击重试。增加连接超时只能缓解冷启动慢，
不能修复缓存目录冲突。
