# npx 冷启动失败调查（2026-11-16）

用户反馈测试台初始化失败或工具列表为空。以下记录仅保留非敏感版本、时间与错误类型，
不包含用户的数据库地址、账号、密码或完整配置。

## 用户日志确认的直接故障

- Node 20.20.2 / npm 10.8.2，命令为 `npx -y @benborla29/mcp-server-mysql`。
- 本次解析版本 2.0.9，大量依赖为 cache miss；主包下载耗时 20682ms。
- 11:23:00 和 11:23:10 有两次重叠 MCP 连接，11:23:18 出现重复 npm 弃用警告。
- 11:23:25 测试台 `TimeoutError`；11:23:39 npm 解包阶段失败，
  `_npx/57e5b9c57ed85305/node_modules/aws-ssl-profiles/lib` 的 `rmdir` 报 `ENOTEMPTY`。
- 这份日志没有 MySQL 网络、权限或认证错误，不能据此要求用户修改数据库配置。
  307 是路径尾斜杠重定向；传输层 200 不代表上游初始化成功。

## 升级相关行为变化

Git 提交 `5fc2525`（2026-10-18）同时升级 FastMCP 3.4.4 → 4.1.0 并重写代理工厂：

- 升级前使用 `create_proxy(mcp_config)`。核对本地缓存的 3.4.4 源码：
  `_create_client_factory` 返回 `base_client.new()`，Client.new 使用浅复制，
  底层 MCPConfigTransport 及其 stdio transport 被共享；stdio 默认 keep_alive=True。
- 升级后 `make_proxy_client_factory` 每次创建独立 transport/client，显式 keep_alive=False。
- 同一次提交为测试台初始化新增 `anyio.fail_after(25)`，客户端 timeout=30；
  旧路径没有这一额外总期限，3.4.4 默认初始化期限为 None。
- Node 20.x 安装路径在升级前已存在，未发现此升级显式引入 npm 10.8.2 的证据。

为隔离依赖版本变量，在同一当前依赖环境、同一个无外部连接的 FastMCP stdio 夹具上，
分别模拟旧工厂的共享 transport 与当前独立工厂，连续执行四次工具查询：
旧策略启动 1 个子进程，当前策略启动 4 个子进程。探针临时文件
`/private/tmp/mcpcat-stdio-strategy/probe.py` 不作为正式产品文件发布。
这验证了工厂策略改变进程启动次数，没有对用户数据库执行连接或查询，
也没有直接复现用户 npm 缓存的损坏。

## 归因与修复方向

直接故障是 npm 缓存安装失败，升级中的进程策略变化很可能提高了触发概率，
固定初始化期限又使首次安装更容易提前结束。不将问题简单归咎于用户配置，
也尚无证据确认 FastMCP 4.1.0 自身存在该 npm 缓存故障。
[npm #8224](https://github.com/npm/cli/issues/8224) 记录相同包并发安装的 ENOTEMPTY 风险；
[npm 11.6.1 变更记录](https://docs.npmjs.com/cli/using-npm/changelog/#1161-2025-09-23)
列出并发 non-local npx 修复。

## 已实施的启动策略

- 每次连接继续创建独立进程、协议会话和用户回调，不共享身份或 roots。
- `npx` 从启动到协议协商完成使用 OS 文件锁排队，协商完成立即放行；
  工具调用本身仍可并行。同一数据库路径的多个 worker 共用此锁。
- 排队与初始化共用 120 秒预算；普通工具请求保持原配置的超时。
  测试台外层请求预留启动和操作时间，前端 HTTP 等待为 180 秒。
- 启动失败保留异常并返回失败，不再将上游发现异常伪装为空工具列表。
- 超时、取消与异常均释放锁、回收子进程；stderr 进入脱敏诊断日志。

此策略不自动删除已有损坏缓存。不同数据库路径的独立部署如果共享 npm 缓存，
应使用独立缓存或统一外部启动协调；本应用的锁不跨这些部署生效。
已有缓存损坏时，停止相关连接并保留 debug 日志，再由维护者处理对应缓存。
镜像中预安装固定版本并直接运行入口，仍可减少网络下载和冷启动时间。
